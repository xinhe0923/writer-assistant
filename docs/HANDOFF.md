# 交接：「断点续写」小说写作套件 · Phase 0

> 写于 2026-10-18。用法：上传到 Claude Code **Projects** 的 library，让 Project 按这份文档实现 Phase 0；我自己也照第 1 节操作。
> 读这份文档不需要看之前的对话。

## 0. 目标

在一个私有 git 仓库里搭一个轻量写作套件：AI 负责**记忆、提问、查设定、写摘要**，**正文只由我写**。
目的：在等 agent 的 10–15 分钟空档里，2 分钟内接上进度；卡住时有出路；每次写的字都被记下来。

## 2. 启动提示词（粘贴到 Project 对话）

```
请先完整阅读 library 里的 HANDOFF.md。方案已经定好，这次只实现 Phase 0：在我连接的私有仓库里搭「断点续写」小说写作套件。

1. 先给我一个不超过 10 行的执行计划（用几个 thread、各做什么），我确认后再动手。
2. 最多 2 个 thread，能串行就串行，避免合并冲突、节省额度。
3. 第 3 节「已定决策」不要重新讨论；第 7 节「这次不做」的内容不要做。

5. 不确定的 Claude Code 用法（自定义命令放 .claude/commands 还是 .claude/skills、frontmatter 支持哪些字段、能否按命令指定 model），先查当前官方文档再写，并在报告里写明查到的结论。
6. 做完后按第 5.1 节逐条报告验收结果；把第 3 节的决策记进项目记忆。
7. 交付方式：所有改动合并成一个 PR（目标分支 main），PR 描述里附验收清单的结果；我审完自己合并，你不要直接推 main。
8. 遇到只有我能决定的事（第 9 节之外的新问题），不要猜，停下来在对话里问我；其余按文档自己决定，不用逐步向我确认。
```

## 3. 已定决策（不要重新讨论）

| 决策 | 理由 |
|---|---|
| AI 不写正文，只做记忆、提问、给方向、查设定、写摘要、指出错别字 | 2026 年国内平台在严打 AI 正文（见第 10 节）；我写小说首先是为了表达和减压 |
| 先写短篇（1–1.5 万字），不开长篇连载 | 短篇整篇放得进 AI 上下文，断档和卡文风险小；字数门槛和碎片时间的产量（约 900 字/天，推测）对得上 |
| 轻量套件：Markdown + 4 个命令 + 1 个字数脚本 + git | 搭建 ≤2 小时；最大的风险是「造工具代替写作」 |
| 命令名用英文：`/go` `/stuck` `/done` `/lore` | 避免和 Claude Code 自带命令冲突（自带有 `/resume`） |
| git 管理，每次收工提交并推到私有远程 | 提交历史就是创作过程证据（区分「辅助」和「代写」主要看过程证据）；也让 Project 和本地保持同步 |
| 正文和记忆分开提交 | 让「正文提交里只有我写的字」一目了然 |
| 日常写作在**本地**会话里做；Project 只负责搭建和以后的异步任务 | Projects 目前只在云端运行；写正文要用本地编辑器；10 分钟空档要的是快 |

### 4.2 CLAUDE.md（照抄）

```markdown
# 小说仓库 · 你是写作搭档，不是代笔

## 铁律
1. 不写正文：不写叙述、描写、对白，也不写「示范段落」，即使我要求。正文只由我写。
2. 你可以：提问、给一句话的方向、查设定（必须注明 文件:行号）、写摘要、维护 设定/ 摘要/ 断点.md 日志.csv、指出错别字（只指出位置，不改写）。
3. 不修改 正文/ 下的任何文件。
4. 每次会话先读 断点.md；不要通读全文，需要时再按需读取。
5. 查不到就说查不到，不编造设定。

## 提交
- 正文提交：只含 正文/ 的改动，信息为「正文：<文件> +<N>字」，不加 Co-Authored-By。
- 记忆提交：其余改动，信息为「记忆：<简述>」，结尾加 Co-Authored-By 行。
- 有远程仓库时，提交后 push。

## 输出
- 中文，简短。/go 和 /done 的输出不超过 250 字。
```

### 4.3 模板

`断点.md`

```markdown
# 断点
- 位置：（文件 + 停在哪一幕，一句话）
- 下一句开头：（我写的，原样保留）
- 下一个小任务（10–15 分钟，300–800 字）：
- 没解决：
  - [ ]
- 今日字数：0
- 更新时间：
```

`大纲.md`

```markdown
# 大纲
- 一句话梗概：
- 主角：想要 / 害怕 / 秘密
- 结局方向（大致即可）：
- 目标字数：10000–15000

## 节拍表
| # | 节拍 | 要发生什么（一句话） | 目标字数 | 状态 |
|---|---|---|---|---|
| 1 | 钩子（开头 300 字内抓住人） | | 800 | |
| 2 | 起：主角和困境 | | 2000 | |
| 3 | 第一次反转 | | 2000 | |
| 4 | 升级 | | 2500 | |
| 5 | 至暗时刻 | | 2000 | |
| 6 | 真相 / 第二次反转 | | 2500 | |
| 7 | 结局与余韵 | | 1500 | |
```

`设定/人物.md`（每个人物一块）

```markdown
## 名字
- 一句话：
- 想要 / 害怕：
- 说话习惯：
- 当前状态（/done 维护）：
- 作者真相：（只有我知道的）
- 读者已知：（截至目前读者知道的）
```

`设定/伏笔账本.md`

```markdown
| 伏笔 | 埋在（文件:行） | 计划在哪回收 | 已回收（文件:行） | 读者已知？ |
|---|---|---|---|---|
```

`设定/世界观.md`：「规则（不能违反的）」和「地点」两个列表。
`灵感箱.md`：按日期记的列表。
`摘要/001.md`：标题 + 不超过 200 字、只写正文里已经发生的事。

### 4.4 命令规格

每个命令文件都写 `description`；有参数的写 `argument-hint`；如果当前文档支持，用 `model` 指定模型（别名 `sonnet`/`opus` 或完整 ID `claude-sonnet-5-5`/`claude-opus-5-5`，以文档为准）。

**`/go`（开工）** · Sonnet

1. 有远程就 `git pull --ff-only`；失败就提示一句，继续用本地内容。
2. 读 断点.md。如果还是空模板，走下面的冷启动。
3. 只读：当前章最后约 500 字；断点里提到的人物在 设定/人物.md 的条目。
4. 向 日志.csv 追加一行 `go`（delta 为 0）。
5. 按固定格式输出（≤250 字）：
   - 【前情】≤150 字
   - 【停在】文件 + 引用我写的最后一句
   - 【下一句开头】
   - 【这次的小任务】一个，10–15 分钟能写完
   - 【不想写这个？】两个备选，例如「写一段你最想写的对白」「往灵感箱丢三个画面」
   - 【没解决】最多 3 条
6. 不写任何故事正文（引用我写过的原文除外）。

冷启动：一次问 4 个问题：一句话梗概？主角想要什么、怕什么？结局大致方向？第一场戏是什么画面？→ 用我的原话整理进 大纲.md（我说「没想好」时，可以给 3 个一句话的选项让我挑）→ 创建空的 `正文/001.md` → 写 断点.md，第一个小任务是节拍 1。

**`/stuck`（卡住了）** · Opus · 参数：卡在哪（可选）

1. 读 断点.md、大纲.md、当前章最后约 1000 字、相关设定。
2. 向 日志.csv 追加一行 `stuck`。
3. 第一轮：针对当前情况问 3 个问题，从题库里挑或改写：角色此刻最想要什么？最糟会发生什么？读者此刻预期什么，怎么反着来？这场戏结束时什么变了？谁在这场戏里藏着秘密？然后等我回答（我说「直接给」就跳到第 4 步）。
4. 第二轮：给 5 个方向，每个一句话（≤40 字），分别标「顺 / 逆 / 狠 / 暖 / 怪」。只说「发生什么」，不写对白和描写。
5. 还不行：建议我在正文里自己打上【待定：一句话】先跳过，并告诉我可以先写哪一幕；把这个卡点记进 断点.md 的「没解决」。
6. 不修改 正文/。

**`/done`（收工）** · Sonnet · 参数：下一句开头（可选）

1. 运行 `python3 tools/wordcount.py --log`，得到本次各文件新增字数和总字数（脚本写入 日志.csv）。
2. 用 `git diff HEAD -- 正文/` 看这次写了什么。
3. 更新 `摘要/<章>.md`（≤200 字，只写正文里发生的事）。
4. 只根据正文里的事实，更新 设定/人物.md 的「当前状态」和「读者已知」；有新伏笔或回收就更新 伏笔账本.md。拿不准的标「待确认」，不要追问我。
5. 下一句开头：有参数就用参数；没有就问我一次。我回车跳过的话，写一句「方向」并标明这是方向，不是句子。
6. 重写 断点.md；下一个小任务取 大纲.md 里下一个没完成的节拍。
7. 两次提交：先正文提交（只含 正文/，没改动就跳过），再记忆提交（其余改动）；有远程就 push。
8. 输出 ≤5 行：今天 +N 字（累计 M）/ 下次从哪开始 / 下一个小任务。
9. 不修改 正文/。

**`/lore`（查设定）** · Sonnet · 参数：问题

1. 在 设定/ 摘要/ 正文/ 大纲.md 灵感箱.md 里搜索。
2. 回答 ≤100 字，每条事实都注明 `文件:行号`。
3. 找到互相矛盾的说法：都列出来，标「设定冲突」。
4. 找不到：说「没查到」，并建议应该记在哪个文件。

### 4.5 `tools/wordcount.py`

- 只用 Python 标准库，支持 Python 3.9+。
- 字数口径：`正文/*.md` 里的非空白字符，去掉 Markdown 标记（标题的 `#`、强调的 `*` `_`、链接语法）、HTML 注释和【待定：…】占位；标点算字。口径写进 README，以后可以改。
- 默认比较工作区和 HEAD（用 `git show HEAD:<path>` 取旧内容）：新文件全算，删除的文件算负数，还没有 HEAD 时全算。
- 调用 git 时都加 `-c core.quotepath=false`。
- `--log`：每个有变动的文件向 日志.csv 追加一行 `date,time,done,<file>,<delta>,<total>`，total 为改动后整个 正文/ 的字数。
- 测试 `tests/test_wordcount.py`（用 `python3 -m unittest` 运行）覆盖：新文件、修改、删除、Markdown 标记不计、【待定】不计、中文路径、没有 HEAD 的空仓库。

## 6. 模型和额度

依据：Anthropic 自己说过 Projects 的并行 thread 会更快耗尽额度；写小说和工作 agent 共用同一份额度。

- **搭建（Project）**：coordinator 用 Opus 5.5 + high effort 就够；worker 只写 Markdown 和一个小脚本，medium effort 即可；thread 不超过 2 个。最高 effort 留给真正难的工作任务。
- **日常命令**：`/go` `/done` `/lore` 用 Sonnet 5.5（空档里等 AI 想一分钟很亏）；`/stuck` 用 Opus 5.5（需要好点子）。如果命令文件不支持指定 model，就把本地写作会话默认设成 Sonnet，卡住时手动切到 Opus。

## 7. 这次不做（Phase 0 范围外）

- SessionStart hook 自动注入断点、`/check` 一致性检查、`/proof` 错别字检查 → Phase 2
- 手机灵感收集、desktop app 插件 → Phase 3
- 向量检索、RAG、数据库、网页应用 → Phase 4，而且只在写长篇超过约 20 万字时才做
- 多 agent 自动写章节、「去 AI 味」、任何形式的 AI 正文或示范段落 → 永远不做

## 8. 之后的阶段

| 阶段 | 时间 | 内容 |
|---|---|---|
| 1 | 搭完后 2 周 | 只写，不改工具（最多改提示词）。目标：一篇 1–1.5 万字的短篇初稿 |
| 2 | 第 3–4 周 | 只为真实遇到的痛点加功能：SessionStart hook、`/check`、`/proof`；每周让 Project 在云端做一次全书一致性复查，只出报告、不改文件 |
| 3 | 可选 | 手机灵感收集；agent 运行时显示当前小任务和今日字数的 desktop 插件 |
| 4 | 仅长篇 | 状态文件 + 检索（参考 webnovel-writer） |

**Phase 1 看三个指标**（数据来自 日志.csv）：
- 恢复时间：从打开到写出第一句不到 3 分钟（自评）
- 每周字数：用真实数据重算产量，替换「900 字/天」这个推测
- 卡住多久能继续：`stuck` 到下一次 `done` 的间隔

**退出条件**：2 周后恢复时间仍超过 5 分钟，或总字数不到 5000，就停止加功能，改试 NovelCrafter（21 天免费）对比。

## 9. 待我决定
